# x402 on GuardPay

GuardPay runs an **x402 facilitator**: it verifies signed payment
authorizations and settles them on-chain. Any resource server can point at it.

x402 is an open protocol, not a product. A server answers `402 Payment
Required` with its terms; the client retries carrying a signed authorization;
a facilitator checks that signature and broadcasts it.

Settlement uses EIP-3009 `transferWithAuthorization`. The payer signs, GuardPay
submits and pays the gas, and the tokens move payer → payee **directly**.
GuardPay never takes custody and never sees the payer's key.

## Endpoints

Base URL: `https://your-guardpay-host/api/x402`

### `GET /supported`

What this facilitator can settle.

```json
{
  "kinds": [{ "x402Version": 2, "scheme": "exact", "network": "eip155:84532" }],
  "extensions": [],
  "signers": { "eip155:*": ["0x…"] }
}
```

### `POST /verify`

Check an authorization without moving anything. Call this before serving a paid
response.

```json
{ "paymentPayload": { … }, "paymentRequirements": { … } }
```

Returns `{ "isValid": true }`, or `{ "isValid": false, "invalidReason": "…" }`
with a specific reason — `invalid_exact_evm_signature`,
`invalid_exact_evm_insufficient_balance`,
`invalid_exact_evm_payload_authorization_value_mismatch`, and so on.

A `400` means the request could not be read at all, and a `502` means the
facilitator itself failed. Neither is reported as `isValid: false` — a caller
should never be told their signature was rejected when it was never checked.

### `POST /settle`

Broadcast the authorization. Same body as `/verify`.

Returns the scheme's settle response, including the transaction hash.

A replayed authorization is refused with `409` and
`errorReason: "payment_already_settled"`, returning the original transaction
hash. The token contract would reject a reused EIP-3009 nonce anyway, but only
after a broadcast has already cost gas — this refuses it beforehand.

### `GET /fees`

What the facilitator charges: `{ "bps": 100, "minAtomic": "0", "payees": "any", … }`.

### `GET /payments` *(authenticated)*

Per-request payments taken through the facilitator, for the merchant
dashboard, with totals. Each settled payment carries the `fee` it accrued, and
`stats.fees` is the running total owed.

## Fees

The transfer goes payer → payee directly, so GuardPay can't take its cut
on-chain. Instead each settlement for a registered merchant accrues a fee of
`X402_FEE_BPS` (default 1%), floored at `X402_FEE_MIN` atomic units, fixed at
settlement time. Payees with no GuardPay account accrue nothing. Set
`X402_PAYEES=merchants` to stop settling for them at all.

## Payload shape (x402 v2)

The agreed terms travel on `accepted`:

```json
{
  "x402Version": 2,
  "resource": { "url": "https://api.example.com/v1/forecast", "method": "GET" },
  "accepted": {
    "scheme": "exact",
    "network": "eip155:84532",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "amount": "10000",
    "payTo": "0x…",
    "maxTimeoutSeconds": 60,
    "extra": { "name": "USDC", "version": "2" }
  },
  "payload": {
    "signature": "0x…",
    "authorization": {
      "from": "0x…", "to": "0x…", "value": "10000",
      "validAfter": "0", "validBefore": "1780000000", "nonce": "0x…"
    }
  }
}
```

v1 payloads (scheme/network at the top level, `maxAmountRequired`) are still
recorded correctly, but v2 is what the bundled schemes expect.

## Webhooks

A settled payment whose `payTo` matches a known merchant fires `x402.settled`
on their configured webhooks, signed like every other GuardPay webhook.

## Configuration

| Variable | Purpose |
|---|---|
| `X402_NETWORKS` | CAIP-2 networks to serve. Defaults to Base Sepolia only. |
| `X402_CONFIRM_TIMEOUT_MS` | Receipt-wait bound. Keep below any gateway timeout. |
| `X402_FEE_BPS` | Fee per settlement, basis points. Default 100 (1%). |
| `X402_FEE_MIN` | Fee floor per settlement, atomic units. Default 0. |
| `X402_PAYEES` | `any` (default) or `merchants` to settle only for registered payees. |
| `OPERATOR_PRIVATE_KEY` | Relayer that pays gas. Falls back to `m/44'/60'/7'/0/0` off `MASTER_SEED`. |

**The relayer needs gas.** Verification is free; settlement is a transaction,
and it fails if the operator address is unfunded.

## Not done yet

- Solana (`@x402/svm`) is installed but not registered — EVM only today.
- Accrued fees are tracked, not yet collected; there is no invoice or
  deduction flow for them.
- The `upto` scheme (metered billing) is not wired up; only `exact`.
- The endpoints are unauthenticated by design. Put a rate limit in front of
  them before exposing this publicly, or settlement gas becomes a DoS surface.
